# 效果基线（真实模型）

这份文档记录**可复现的基线证据**，不是文学结论。原始输出保存在本地 `bench/runs/`（已被 `.gitignore` 忽略，不随仓库分发）。

## 环境与口径

- 模型服务：本机 OpenAI-compatible 代理（`http://127.0.0.1:7863/v1`）
- 基线模型：`cn:glm-5.3`
- 日期：2026-11-06
- 管线：当前 `main` 分支实现，`--workflow p0`（只测写作管线，不触发抽取/审查）
- 超时/输出：`timeout-ms=180000`、`max-output=8192`
- 密钥只从环境变量读取，未写入任何项目文件或基线产物（已检查）

复现命令：

```bash
WEAVE_API_KEY=... node scripts/benchmark.ts run \
  --suite craft --seed harbor-ledger \
  --mode real --base-url http://127.0.0.1:7863/v1 \
  --model cn:glm-5.3 --timeout-ms 180000 --max-output 8192 \
  --out bench/runs/real-baseline-craft-glm
```

## 正文工艺集（craft / harbor-ledger）

4 章、7300 字、写入耗时 147.5 秒、4361 输入估算 tokens、0 次重试。

| 章 | 字数 | 耗时 | 对白占比 | 结尾形态 |
| --- | --- | --- | --- | --- |
| 1 | 1996 | 33s | 18.6% | 动作 + 空间移动（往港口走） |
| 2 | 2097 | 55s | — | 具体物证 |
| 3 | 1765 | 38s | — | 画面收束，未解释 |
| 4 | 1442 | 21s | — | 引语 + 未完成动作 |

观察：

- 合同节点（缺页、周砚、老谭、空箱、照片）均落实；没有出现总结式收束。
- 字数落在目标 1800 的 0.8–1.17 倍，明显比 `deepseek-v4-pro` 更贴合同口径。
- 场景不同导致对白比例显著不同，不支持“统一对白比例”的机械写法。
- 第 1 章结尾是行动而非解释，符合 `endingStrategy`。

### 模型可用性观察（非基线）

同一管线用 `cn:deepseek-v4-pro` 跑同一 craft 种子：7804 字、525.9 秒、1 次 120 秒超时重试；第 3 章耗时 300 秒。随后长篇运行中多次出现“只返回 reasoning、正文为空”的响应。

这暴露了两个真实问题，均已修复：

- 空正文（reasoning-only）原先在写作层直接失败；现在在**首个 delta 前**按可重试处理，最多重试 3 次。
- 120 秒超时对慢速推理模型偏紧；基线改用 180 秒，并在 `benchmark` 提供 `--timeout-ms` / `--max-output`。

## 模型可用性观察：Gemini 兼容层（2026-11-09，非基线）

用 Google 官方 OpenAI 兼容层（`https://generativelanguage.googleapis.com/v1beta/openai`）跑 `craft / broken-cultivation`，用于验证多 provider 接线，不作为质量证据：

| 模型 | 结果 | 说明 |
| --- | --- | --- |
| `gemini-2.5-flash` | 4 章 9097 字 / 108 秒 / 0 重试 | 第 4 章在 2/3 次重复中以 blocking `TRUNCATED_ENDING` 阻断（"根看不见的细线，轻轻拨动"）；流式不返回 usage，tokens 为本地估算 |
| `gemini-3.5 / 3.6 / 3.7 / 3.8-flash` | 未取得样本 | 模型列表中存在，但 `generateContent` 返回 503 或兼容层请求超时 |

结论：

- 兼容层接线可用，速度不慢于本机代理（同种子 craft 基线 147.5 秒）；
- 章末截断是真实缺陷，需按 `max-output` 与内容检查处理，不能当成"模型文风问题"；
- 自 2026-11-09 起运行记录写入 provider 的 `finish_reason`。同日复跑 12 次：6 次 `stop`、1 次 `length`，`length` 那次同时触发 `TRUNCATED_ENDING`——截断可直接定位为输出上限，不再靠标点推断；
- 3.x 系列当前不可用，与本项目配置无关，择期重试；
- 该观察与 deepseek 那条同级：只说明可用性，不参与默认值裁决。

## 长篇纵向集（longitudinal / long-harbor）

30 章合成前文（用于验证检索与记忆接线，不参与文学评价）+ 3 章真实生成。

3 章、5296 字、写入耗时 140.8 秒、3977 tokens、0 次重试。

| 章 | 字数 | 耗时 | 检索到的定稿证据 |
| --- | --- | --- | --- |
| 31 | 1591 | 28s | ch-002 / ch-007 / ch-012 / ch-017（同一合成 beat 的重复版本） |
| 32 | 2008 | 81s | ch-004 / ch-009 / ch-014 / ch-019（同上） |
| 33 | 1697 | 31s | ch-031 的 4 个段落（全部来自同一章） |

观察：

- 召回命中 1/3（与假模型一致），漏掉的两项都是被同 beat 的重复段落挤出名额，而不是查询词不相关。
- 检索没有“来源多样性”约束：4 个名额可以全部来自同一章或同一段落的重复版本。这是当前最值得修的检索质量问题。
- 本 seed 各章地点不同，安全衔接按规则降级为 `pov:previous-summary`，没有注入定稿原文——符合保守策略。
- **第 32 章正文在句中断开**（结尾无终止标点，并带一个不完整 UTF-8 字符），模型流被上游截断，而 p0 管线不跑内容检查，因此被直接定稿。

这次截断暴露了两个真实缺陷，均已修复：

- 流结束时没有 flush `TextDecoder`，最后一个多字节字符可能变成 `�`；
- 内容检查不识别“句中断开”，现在会以 blocking `TRUNCATED_ENDING` 阻断定稿（p05 起生效）。

### 检索多样性修复后的复跑

对同一 seed 复跑（GLM，30 章合成前文 + 3 章真实生成）：3 章 8371 字、137.7 秒、0 重试。

| 章 | 字数 | 检索到的定稿证据 |
| --- | --- | --- |
| 31 | 3106 | ch-001 / ch-002 / ch-003（三个不同章节） |
| 32 | 3003 | ch-004 |
| 33 | 2262 | ch-031 的两段（每章上限 2 生效） |

- 修复前：4 个名额全部来自同一 beat 的重复版本；修复后：重复被压缩到 1 段，名额分配给不同章节。
- 章节级召回仍为 1/3：合成语料把同一 beat 复制到多章，“期望章节”本身有歧义；这次修复减少的是名额浪费，不能靠这份种子证明召回率提升。
- 真实书稿上的收益仍需人工盲评与更真实的纵向语料，而不是继续加合成重复。

## 番茄目标种子与 holdout

2026-11-06 新增原创种子 `fanqie-rewind-ten-minutes`：4 章都市脑洞，目标读者、核心承诺、评测焦点、材料政策和 `holdout: true` 均在种子中声明。评测重点是开篇异常、回退选择是否产生新证据、反击是否写到对方反应，以及章末问题是否具体。

种子的材料政策禁止使用任何参考作品原文；真实旧稿必须另行记录来源与授权，不与本种子混报。benchmark 的运行 JSON、汇总 JSON 和 Markdown 报告都会保留这些元数据，holdout 不会被换算成评分。

该种子已通过 fake 模式的四章端到端回归，仅证明管线与元数据接线，**尚未进行真实模型生成，不构成正文效果证据**。真实运行前仍需作者确认模型、预算和材料范围，并保留原始输出；本种子作为 holdout，不用于逐轮调参。

### 玄幻组粗读反馈（未逐组打分）

换成玄幻种子 `broken-cultivation` 后，读者粗读四组的反馈：

- 左栏整体略好，但没有逐组判定；
- 两版都有“莫名其妙描写环境”的问题。

解封 mapping 后：ch1–ch3 的左栏是 `json`，ch4 的左栏是 `mission`。也就是说，粗读信号偏向 `json` 或至少不支持 `mission` 更好。

处理：

- `promptRenderer` 默认保持 `json`，不翻转；
- 不把粗读当作胜率，也不写进 `benchmark score`；
- 针对两版共有的问题，在共享 system prompt 中加入“环境描写必须改变处境/提供信息/制造压力，开篇直接进入动作或问题”；
- 效果审查新增“环境与描写”维度；
- 内容检查新增 `ENVIRONMENT_OPENING` 警告（开篇连续环境铺陈，仅警告不阻断）。

下一步若要让这条反馈变成可验证结果：用同一玄幻种子重跑 `json`，对比开篇与环境段落密度，再做一次盲评。

## 关键词召回探针

为判断是否需要语义检索，做了两次对照探针（本地假模型，只测召回）：

1. **6 章规模**：前文用“旧册子写着每次靠岸前压了多深的水”，后文查询“核对船只载重记录”。目标段落未被召回，反而召回了一章不相关的雨夜（仅因单字“下”命中）。
2. **30 章规模**：前文用“父亲把每回守卫交接的时刻抄在烟盒背面”，后文查询“确认看门人什么时候换班”。目标段落被召回，但只靠单字“时”命中，属于偶然相通。

结论：

- 关键词检索的漏召与误召都真实存在，但**不是稳定的语义鸿沟**：同一类改写在一个规模上漏、在另一个规模上靠单字命中。
- 更紧迫的问题不是“没有向量”，而是**单字匹配噪声与近重复段落挤占名额**：长篇实跑中曾出现 4 个检索名额被同一段落的重复版本占满（ch-002/ch-007/ch-012/ch-017 为同一合成 beat）。
- 因此 `optional-semantic-retrieval` 的启动条件（稳定、影响正文的召回缺口）**尚未被证明**，保持不实施。

## 分段生成放量实验（设计已定，真实数据未采集）

2026-11-07 新增固定三组样本，用于回答“分段是否更少截断、更少门禁失败、是否值得多花成本”：

| 组 | seed | 目标字数 | 计划段数 | 说明 |
| --- | --- | --- | --- | --- |
| S | `segmented-rollout-s` | 3000 | 2 | 普通章 |
| M | `segmented-rollout-m` | 6000 | 3 | 长章 |
| L | `segmented-rollout-l` | 9000 | 5 | 压力章 |

固定条件：同一合同、同一已批准节拍、同一模型与温度；只改变 `draftingStrategy`。每组至少 3 次，记录中位数与失败样本。

一条命令复跑（先 prose-first，再 segmented，最后用 `pairs`/`score` 做盲评）：

```bash
WEAVE_API_KEY=... node scripts/benchmark.ts run \
  --suite segmented-rollout --strategy prose-first \
  --mode real --base-url http://127.0.0.1:7863/v1 \
  --model cn:glm-5.3 --timeout-ms 180000 --max-output 8192 \
  --out bench/runs/segmented-rollout-prose

WEAVE_API_KEY=... node scripts/benchmark.ts run \
  --suite segmented-rollout --strategy segmented \
  --mode real --base-url http://127.0.0.1:7863/v1 \
  --model cn:glm-5.3 --timeout-ms 180000 --max-output 8192 \
  --out bench/runs/segmented-rollout-segmented
```

当前状态：

- 已用 fake 模式跑通三组（2/3/5 段、0 失败），只证明审批流、分段计划、写入与报告接线；**不是效果证据**。
- 真实模型运行、门禁统计、盲评均**未采集**。
- 因此放量裁决为：**保持显式 `--strategy segmented` opt-in，不改为默认路径**。

放量门槛（同时满足才升级）：

1. L 组完成率 ≥95%；
2. 段级首次通过率 ≥90%；
3. 合并稿门禁通过率不低于单次路径；
4. 总成本 ≤单次路径的 1.25 倍；
5. 至少 1 轮盲评留痕，且没有“分段明显更差”的一致结论。

报告中的 `segments` / `failed` 来自写入返回的真实分段状态；`usage` 来自真实模型返回；门禁数据需在真实运行后从阶段报告中补齐。报告同时区分 `mode: fake` 与 `mode: real`，fake 不得用于阅读效果结论。
