# 生成可批准的滚动章纲与合同

## 任务目标

消除逐章手写 JSON 的瓶颈，让作者从已批准的 StoryPromise、VolumeArc 和 RollingPlan 生成下一批章纲候选，并经检查后批准为 ChapterContract。

## 工作流

```text
已批准故事与卷弧
  → 生成下一批 RollingPlan / 章纲候选
  → 作者编辑
  → 结构与账本预检
  → 作者按具体内容哈希批准
  → 现有 ChapterContract 与写作流程
```

默认只生成下一小批章节，最近约 3 章达到可写详度，后续保留滚动调整空间。不提供“一键生成五百章详细合同并全部生效”。

## 命令边界

提供查看、生成、检查和批准的统一 `weave outline` 入口。生成与批准是不同操作；生成命令不得隐式批准，也不得直接覆盖已批准合同或已定稿章节。

生成运行保存模型、输入规划版本、候选哈希和失败原因。重复生成产生新候选，不覆盖作者已编辑内容。中断后可以基于已保存候选继续，而不是重新生成整批。

## 预检

候选在批准前检查：

- 章号、字段和连续性；
- 人物登场、死亡和显式知识边界；
- 本卷目标、故事线和 ReaderPromise 推进关系；
- 与已定稿事实、OpenLoop 和前一章实际结尾的冲突；
- 近章详略是否足够生成正文。

语义上的“是否精彩”只给建议，不作为自动批准依据。

## 上下文与出处

生成器可以读取作者版全局规划，但这不表示后续 limited POV 正文也能读取相同秘密。批准后的章合同继续由现有材料准入执行 POV 过滤。

候选保持 `generated` 出处；只有批准后的具体哈希转为作者规划。正文生成拒绝使用未批准合同。

## 验收

- 可以从一个已批准卷弧生成下一批章纲候选，候选不会直接改变正式合同。
- 作者编辑后，检查和批准绑定编辑后的哈希。
- 未批准、检查失败或引用未知知识的候选不能进入正文写作。
- 重跑不会覆盖作者修改、已批准合同或定稿历史。
- 远期计划可以调整而不批量改写近期已批准合同。
- 现有 `contract check`、CLI JSON 和退出码语义保持可复用。

## 非目标

- 不自动决定整本书所有后续剧情。
- 不为了吞吐引入草稿态事实账本或绕过 N-1 定稿依赖。
